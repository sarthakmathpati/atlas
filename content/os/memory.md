## os.memory.logical-vs-physical-addresses
name: "Logical vs physical addresses"
importance: must
scope: "MMU and address binding"

### simple
A program uses logical addresses, which are like apartment numbers in its own private building, while the hardware stores data at physical addresses, the real locations on the street. A translator in the CPU, the memory management unit, converts one to the other on every access. This lets every program believe it has memory starting at zero, all to itself.

### interview
- A **logical (virtual) address** is what the CPU generates while running a program; a **physical address** is the actual location in RAM that the memory unit sees.
- The **MMU** (memory management unit) translates every logical address to a physical one at runtime, using base and limit registers in simple systems or **page tables** (cached in the **TLB**) in modern ones.
- **Address binding** can happen at **compile time** (absolute code; must load at a fixed place), **load time** (relocatable code; addresses fixed when loaded) or **execution time** (addresses translated on every access; needed so a process can move in memory, and what modern OSes do).
- Benefits: **isolation** (a process cannot even name another's memory), **relocation** (the OS can place or move processes anywhere), and the basis of **virtual memory** (logical space can exceed physical RAM).
- The simplest scheme, **base and limit** (relocation) registers: physical = base + logical, trapping if logical ≥ limit.
- The set of all logical addresses of a process is its **logical address space**; two processes can use the same logical address for different physical locations.

### deep
#### Intuition

If programs used physical addresses directly, each would have to know where in RAM it was loaded, and any program could overwrite any other. Giving each process its own numbering, starting at zero, and translating in hardware solves both problems at once: programs stay simple and they cannot reach each other.

#### Address binding over time

| when | how addresses become physical | consequence |
|---|---|---|
| compile time | the compiler emits absolute addresses | must load at one fixed place (old MS-DOS `.COM` files) |
| load time | the loader patches relocatable addresses | fixed once loaded; cannot move while running |
| execution time | the MMU translates on every access | processes can be moved, paged and swapped; used by all modern OSes |

#### The simplest MMU: base and limit

```cpp
struct Mmu {
    uint32_t base, limit;          // loaded by the kernel on every context switch
    uint32_t translate(uint32_t logical) const {
        if (logical >= limit) throw out_of_range("protection fault");   // trap to the kernel
        return base + logical;
    }
};

int main() {
    Mmu p1{300040, 120900}, p2{420940, 50000};
    cout << p1.translate(0) << " " << p1.translate(1000) << " " << p2.translate(1000) << "\n";
    // 300040 301040 421940: the same logical address 1000 lands in different places
    try { p2.translate(60000); } catch (const exception& e) { cout << e.what() << "\n"; }
}
```

#### Worked example

| process | base | limit | logical | check | physical |
|---|---|---|---|---|---|
| P1 | 300040 | 120900 | 0 | 0 < 120900 | 300040 |
| P1 | 300040 | 120900 | 1000 | ok | 301040 |
| P2 | 420940 | 50000 | 1000 | ok | 421940 |
| P2 | 420940 | 50000 | 60000 | 60000 ≥ 50000 | trap: protection fault |

The kernel loads `base` and `limit` on every context switch, so each process sees only its own region. Modern systems replace this single region with **paging**, which maps each page separately, but the principle is the same: the hardware checks and translates every access.

#### Seeing it for yourself

```python
import os

x = [42]
print(hex(id(x)))            # CPython's id is the object's (virtual) address
pid = os.fork()
if pid == 0:
    x[0] = 99                # the child writes to "the same" address...
    print("child", hex(id(x)), x[0])
    os._exit(0)
os.waitpid(pid, 0)
print("parent", hex(id(x)), x[0])   # ...but the parent still sees 42
```

Both processes print the same virtual address, yet hold different values: the MMU maps that address to different physical frames after the child's write (copy-on-write).

#### Pitfalls

- Thinking a pointer value is a physical address: user programs only ever see virtual addresses.
- Forgetting the protection role: translation and permission checks (read, write, execute, user or kernel) happen together.

Connects to: paging, TLB, segmentation, virtual memory and demand paging, process vs program.

### questions
Q: What is the difference between a logical and a physical address?
A: A logical or virtual address is generated by the CPU while a program runs and belongs to the process's own address space. A physical address is the actual location in main memory. The memory management unit translates logical addresses to physical ones on every access.

Q: What does the MMU do?
A: The memory management unit is hardware that translates each logical address the CPU issues into a physical address, using relocation registers or page tables, and checks permissions at the same time. An invalid or forbidden access raises a trap to the operating system.

Q: What are the three times at which address binding can happen?
A: At compile time, when the compiler produces absolute addresses; at load time, when the loader fixes relocatable addresses; and at execution time, when hardware translates each address as the program runs. Only execution-time binding lets a process move in memory while running.

Q: How do base and limit registers provide protection?
A: Every logical address is compared with the limit register; if it is too large the hardware traps, otherwise the base register is added to form the physical address. Since only the kernel can load these registers, a process can reach only its own region of memory.

## os.memory.contiguous-allocation
name: "Contiguous allocation"
importance: important
prereqs: [os.memory.logical-vs-physical-addresses]
scope: "first fit, best fit, worst fit"

### simple
Contiguous allocation gives each process one unbroken block of memory. It is like seating groups at a long bench: each group needs enough empty seats side by side. When groups leave, gaps appear, and the question is which gap to seat the next group in.

### interview
- Each process occupies a **single contiguous region**, described by base and limit registers. Free memory is a set of **holes** of various sizes.
- **First fit**: take the first hole big enough. Fast, usually good.
- **Best fit**: take the smallest hole big enough. Leaves the smallest leftover, but creates many tiny useless holes and needs a full search (or a size-ordered structure).
- **Worst fit**: take the largest hole. Leaves a big leftover that may be useful, but generally performs worst in simulations.
- Simulations show first fit and best fit beat worst fit in storage use, and first fit is typically faster. Next fit (continue from where the last search stopped) is a variant.
- All suffer **external fragmentation**: enough total free memory, but no single hole large enough. Remedies: compaction (needs execution-time binding) or non-contiguous schemes like paging.

### deep
#### Worked example (the classic)

Holes of 100, 500, 200, 300 and 600 KB, in memory order. Processes of 212, 417, 112 and 426 KB arrive in that order.

| request | first fit | best fit | worst fit |
|---|---|---|---|
| 212 | 500 → leaves 288 | 300 → leaves 88 | 600 → leaves 388 |
| 417 | 600 → leaves 183 | 500 → leaves 83 | 500 → leaves 83 |
| 112 | 288 → leaves 176 | 200 → leaves 88 | 388 → leaves 276 |
| 426 | no hole ≥ 426: waits | 600 → leaves 174 | no hole ≥ 426: waits |
| holes left | 100, 176, 200, 300, 183 | 100, 83, 88, 88, 174 | 100, 83, 200, 300, 276 |

Here best fit is the only one that places all four, but it also leaves the most tiny holes (83 and 88 KB), which are hard to reuse later.

#### Code

```python
def allocate(holes, requests, strategy):
    holes = list(holes)
    placed = []
    for size in requests:
        fits = [i for i, h in enumerate(holes) if h >= size]
        if not fits:
            placed.append((size, None))                  # must wait
            continue
        if strategy == "first":
            i = fits[0]
        elif strategy == "best":
            i = min(fits, key=lambda k: holes[k])
        else:                                            # worst
            i = max(fits, key=lambda k: holes[k])
        placed.append((size, holes[i]))
        holes[i] -= size                                 # the leftover stays a (smaller) hole
    return placed, holes


for s in ("first", "best", "worst"):
    print(s, allocate([100, 500, 200, 300, 600], [212, 417, 112, 426], s))
```

```cpp
// First fit over a list of holes (start, size); returns the start address or -1.
long firstFit(vector<pair<long, long>>& holes, long size) {
    for (auto& [start, len] : holes) {
        if (len >= size) {
            long at = start;
            start += size;                  // shrink the hole from the front
            len -= size;
            return at;
        }
    }
    return -1;
}
```

#### Freeing and merging

When a process ends, its region becomes a hole; if it borders other holes, they are **coalesced** into one bigger hole. Without coalescing, memory would split into ever smaller pieces.

#### Why paging replaced it

Contiguous allocation needs a hole as big as the whole process and leads to external fragmentation (the 50-percent rule: with first fit, about half as many blocks as are allocated end up wasted as fragments, roughly a third of memory). Paging lets any free frame hold any page, which removes external fragmentation entirely. Contiguous allocation survives in allocators for special cases (DMA buffers, huge pages) and in `malloc` itself.

Connects to: fragmentation, paging, logical vs physical addresses, how malloc works.

### questions
Q: What are first fit, best fit and worst fit?
A: They are strategies for choosing a free hole in contiguous memory allocation. First fit picks the first hole large enough, best fit picks the smallest hole large enough, and worst fit picks the largest hole. They differ in speed and in the leftover fragments they create.

Q: Which placement strategy works best in practice?
A: Simulations show first fit and best fit use memory better than worst fit, and first fit is usually faster because it stops searching early. Best fit tends to leave many tiny holes, and worst fit quickly destroys the large holes that big requests need.

Q: What is the main problem with contiguous allocation?
A: External fragmentation: after many allocations and frees, free memory is split into many small holes, so a request may fail even though the total free memory is enough. Compaction or non-contiguous schemes such as paging are needed.

Q: What is coalescing in memory allocation?
A: When a block is freed, merging it with any adjacent free holes into a single larger hole. This slows the growth of fragmentation and keeps large requests satisfiable.

## os.memory.fragmentation
name: "Fragmentation"
importance: must
prereqs: [os.memory.contiguous-allocation]
scope: "internal vs external, compaction"

### simple
Fragmentation is memory that is free but wasted because of how it is split up. Internal fragmentation is like renting a two-seat table for one person: the extra seat is reserved but unused. External fragmentation is like a restaurant with ten empty seats scattered one by one across the room, so a group of four still cannot sit together.

### interview
- **Internal fragmentation**: wasted space **inside** an allocated block, because blocks come in fixed sizes larger than the request (the unused part of a process's last page, allocator rounding, fixed partitions).
- **External fragmentation**: free memory split into **non-contiguous holes** between allocations, so a request can fail although the total free memory would suffice. It arises with variable-size contiguous allocation (and segmentation).
- **Paging** eliminates external fragmentation (any free frame fits any page) but has internal fragmentation of half a page per process on average; larger pages mean more internal waste but smaller page tables.
- **Compaction** shuffles allocated blocks together to merge holes; it needs execution-time address binding and is expensive (copying memory, pausing processes). Garbage collectors with compaction (Java's) do this for the heap.
- Other remedies: coalescing freed neighbors, buddy allocation, slab allocators (fixed-size object caches), size-class allocators (`malloc`).
- The **50-percent rule** (first fit): for N allocated blocks, about 0.5N blocks are lost to fragmentation, so up to a third of memory can be unusable.

### deep
#### Side by side

| | internal | external |
|---|---|---|
| where the waste is | inside allocated blocks | between allocated blocks |
| cause | rounding up to a fixed block size | variable-size allocation and freeing |
| typical with | paging, fixed partitions, size classes | contiguous allocation, segmentation, heaps |
| fix | smaller blocks or finer size classes | compaction, paging, coalescing |

#### Worked example: internal fragmentation with paging

A process needs 72,766 bytes and pages are 4,096 bytes.

$$72766 = 17 \times 4096 + 3134$$

It needs 18 pages; the last page uses 3,134 bytes, so $4096 - 3134 = 962$ bytes are internal fragmentation. The worst case is a process that needs one byte more than a whole number of pages: nearly a full page wasted. On average about half a page per region.

#### Worked example: external fragmentation and compaction

Memory of 1,000 KB after some processes finished:

```text
| A 200 | free 150 | B 300 | free 100 | C 150 | free 100 |
```

Free total is 350 KB, but the largest hole is 150 KB, so a 250 KB process cannot be placed. Compaction moves B and C down:

```text
| A 200 | B 300 | C 150 | free 350 |
```

Now 250 KB fits. The cost is copying 450 KB and updating B's and C's base registers, which only works if addresses are bound at execution time.

#### Code: measuring both kinds

```cpp
// Internal: bytes wasted when every request is rounded up to a multiple of the block size.
long internalWaste(const vector<long>& requests, long block) {
    long waste = 0;
    for (long r : requests) waste += (block - r % block) % block;
    return waste;
}

// External: free bytes that cannot serve a request of `need` bytes because no hole is big enough.
long unusableFree(const vector<long>& holes, long need) {
    long total = 0, largest = 0;
    for (long h : holes) { total += h; largest = max(largest, h); }
    return largest >= need ? 0 : total;
}

int main() {
    cout << internalWaste({72766, 5000, 4096}, 4096) << "\n";   // 962 + 3192 + 0 = 4154
    cout << unusableFree({150, 100, 100}, 250) << "\n";         // 350: all of it is stranded
}
```

#### Choosing block sizes

| page size | internal waste | page table size | TLB reach |
|---|---|---|---|
| small (4 KB) | low | large | small |
| large (2 MB huge pages) | high for small regions | small | large |

Databases and JVMs often use huge pages for big heaps: internal waste is negligible there and TLB misses drop sharply.

#### Pitfalls

- Mixing up the two: internal is waste inside what you were given, external is free memory you cannot use.
- Assuming paging has no fragmentation at all: it still has internal fragmentation.
- Heap allocators fragment too: long-running programs with mixed object sizes can hold far more memory than they use.

Connects to: contiguous allocation, paging, segmentation, how malloc works, garbage collection.

### questions
Q: What is the difference between internal and external fragmentation?
A: Internal fragmentation is unused space inside an allocated block, caused by rounding requests up to a fixed block or page size. External fragmentation is free memory scattered in small non-contiguous holes between allocations, so a large request can fail even though enough total memory is free.

Q: Does paging suffer from fragmentation?
A: Paging eliminates external fragmentation because any free frame can hold any page. It still has internal fragmentation: the last page of each region is usually only partly used, wasting on average half a page.

Q: What is compaction and what does it require?
A: Compaction moves allocated blocks together so all free memory forms one large hole. It requires that addresses be bound at execution time, so relocated processes keep working, and it is expensive because memory must be copied and processes paused.

Q: A process needs 72,766 bytes with 4 KB pages. How much internal fragmentation is there?
A: 72,766 bytes is 17 full pages of 4,096 bytes plus 3,134 bytes, so it needs 18 pages. The last page wastes 4,096 minus 3,134, which is 962 bytes of internal fragmentation.

Q: How does the page size affect fragmentation and overhead?
A: Larger pages increase internal fragmentation, since more of the last page may be unused, but shrink page tables and extend how much memory the TLB covers. Smaller pages waste less memory inside pages but need bigger page tables and more TLB entries.

## os.memory.paging
name: "Paging"
importance: must
prereqs: [os.memory.logical-vs-physical-addresses]
scope: "pages, frames, page tables, address translation"

### simple
Paging cuts a program's memory into small, equal-sized pages and cuts physical memory into frames of the same size, so any page can go in any free frame. It is like storing a long book in a library where each chapter can sit on any free shelf, as long as an index says which shelf holds which chapter. That index is the page table, and it removes the need to find one big empty space.

### interview
- Logical memory is divided into fixed-size **pages** and physical memory into **frames** of the same size (commonly **4 KB**; also huge pages such as 2 MB and 1 GB).
- A logical address splits into a **page number** $p$ (high bits) and an **offset** $d$ (low bits). With page size $2^n$, the offset is the low $n$ bits.
- The **page table** (one per process) maps page number to frame number, plus bits: **valid**, protection (read, write, execute, user or kernel), **dirty**, **referenced**. Physical address = frame × page size + offset.
- The page table lives in memory, pointed to by a register (the **page-table base register**, CR3 on x86); switching processes changes that register.
- Benefits: no external fragmentation, easy sharing (map the same frame into two processes, as with shared libraries), and the basis for demand paging. Costs: internal fragmentation and **extra memory accesses** for translation, fixed by the **TLB**.
- Page table size example: a 32-bit address space with 4 KB pages has $2^{20}$ pages; with 4-byte entries that is **4 MB per process** for a flat table, which is why multi-level tables exist.

### deep
#### Intuition

Contiguous allocation needs one big hole for a whole process. Paging breaks the process into many small, equal pieces, and any free frame can take any piece. The page table remembers where each piece went, and the MMU looks it up on every access.

#### Splitting an address

With 4 KB pages ($2^{12}$ bytes), the low 12 bits are the offset and the rest is the page number:

```text
32-bit logical address:  | page number (20 bits) | offset (12 bits) |
```

#### Worked example

Page size 4,096 bytes. Page table: page 0 → frame 3, page 1 → frame 7, page 5 → frame 9; other pages invalid.

| logical address | page = addr ÷ 4096 | offset = addr mod 4096 | frame | physical = frame × 4096 + offset |
|---|---|---|---|---|
| 20500 | 5 | 20 | 9 | 36884 |
| 4100 | 1 | 4 | 7 | 28676 |
| 100 | 0 | 100 | 3 | 12388 |
| 8200 | 2 | 8 | invalid | page fault (or segmentation fault) |

In hex it is just bit slicing: 0x3ABC is page 0x3 and offset 0xABC.

#### Code: translation

```cpp
const uint32_t PAGE_BITS = 12, PAGE_SIZE = 1u << PAGE_BITS;

struct Pte { bool valid; uint32_t frame; bool writable; };

optional<uint32_t> translate(const vector<Pte>& table, uint32_t logical, bool write) {
    uint32_t page = logical >> PAGE_BITS;              // high bits
    uint32_t offset = logical & (PAGE_SIZE - 1);       // low 12 bits
    if (page >= table.size() || !table[page].valid) return nullopt;     // page fault
    if (write && !table[page].writable) return nullopt;                 // protection fault
    return (table[page].frame << PAGE_BITS) | offset;
}

int main() {
    vector<Pte> table(8, {false, 0, false});
    table[0] = {true, 3, true};
    table[1] = {true, 7, false};                       // read-only page (like code)
    table[5] = {true, 9, true};
    for (uint32_t a : {20500u, 4100u, 100u, 8200u}) {
        auto p = translate(table, a, false);
        cout << a << " -> " << (p ? to_string(*p) : "fault") << "\n";
    }
    cout << (translate(table, 4100, true) ? "ok" : "write fault") << "\n";   // write fault
}
```

#### The cost and the fix

A flat page table in memory means every load or store needs **two** memory accesses: one to read the page table entry, one for the data. The **TLB** caches recent translations so most accesses need only one. Page tables are also large, so real systems use **multi-level** tables that allocate only the parts in use.

#### Sharing

Two processes running the same program can map their code pages to the same physical frames (read-only). That is how one copy of the C library in RAM serves every process.

#### Pitfalls

- Using decimal division in hex problems: with power-of-two page sizes, just split the bits.
- Forgetting that the page table maps pages to frames, not bytes to bytes.
- Confusing page size with page table entry size when computing page table sizes.

Connects to: TLB, multi-level and inverted page tables, virtual memory and demand paging, fragmentation, memory hierarchy.

### questions
Q: What is paging?
A: A memory management scheme that divides a process's logical memory into fixed-size pages and physical memory into frames of the same size. A per-process page table maps each page to a frame, so pages can be placed in any free frames, which avoids external fragmentation.

Q: How is a logical address translated under paging?
A: The address is split into a page number, the high bits, and an offset, the low bits. The page number indexes the page table to find the frame number, and the physical address is the frame number times the page size plus the offset. Invalid or forbidden entries cause a fault.

Q: What information does a page table entry hold?
A: The frame number plus control bits: a valid or present bit, protection bits for read, write and execute and for user or kernel access, a dirty bit set when the page is written, and a referenced bit set when it is accessed. Some systems add caching and global bits.

Q: How large is a flat page table for a 32-bit address space with 4 KB pages?
A: There are 2 to the power 32 divided by 2 to the power 12, which is 2 to the power 20, or about one million pages. With 4-byte entries the table takes 4 MB per process, which is why multi-level page tables are used.

Q: How does paging allow processes to share memory?
A: Two page tables can map pages to the same physical frame. The operating system uses this to share read-only code such as shared libraries among processes, and for shared memory segments and copy-on-write after fork.

## os.memory.tlb
name: "TLB"
importance: must
prereqs: [os.memory.paging]
scope: "caching translations, hit ratio, effective access time"

### simple
The TLB is a tiny, very fast memory inside the CPU that remembers recent page-to-frame translations. It works like a sticky note on your monitor with the phone numbers you dial most, so you rarely need to open the full phone book. Because programs keep reusing the same pages, most lookups hit the sticky note.

### interview
- The **translation lookaside buffer** is a small associative cache of **page → frame** translations (typically tens to a couple of thousand entries, often in two levels).
- **TLB hit**: translation in about one cycle, then one memory access for the data. **TLB miss**: walk the page table in memory (one access per level), insert the translation, then access the data.
- **Effective access time** with a single-level table: $EAT = h(t + m) + (1 - h)(t + 2m)$ for hit ratio $h$, TLB time $t$ and memory time $m$. With $m = 100$ ns, $t = 20$ ns: 80% hits give 140 ns; 98% hits give 122 ns.
- Hit ratios are usually very high (often above 99%) thanks to **locality**: a 4 KB page covers 1,024 consecutive `int`s.
- On a **context switch** the TLB must be flushed unless entries are tagged with an address-space id (**ASID**, or **PCID** on x86). Changing a mapping requires invalidating it, on all cores (a **TLB shootdown**).
- **TLB reach** = entries × page size; **huge pages** (2 MB) multiply reach by 512 and help large-memory programs.

### deep
#### Intuition

Paging made every memory access cost two: one for the page table, one for the data. That would halve performance. The TLB saves the day because programs are predictable: they loop over the same code and walk arrays page by page, so the same few translations are needed again and again.

#### Worked example: effective access time

Memory access $m = 100$ ns, TLB lookup $t = 20$ ns, single-level page table.

$$EAT = h(t + m) + (1 - h)(t + 2m)$$

| hit ratio $h$ | computation | EAT | slowdown vs 100 ns |
|---|---|---|---|
| 0.80 | 0.8 × 120 + 0.2 × 220 | 140 ns | 40% |
| 0.98 | 0.98 × 120 + 0.02 × 220 | 122 ns | 22% |
| 1.00 | 120 | 120 ns | 20% (just the TLB time) |

With a four-level page table, a miss costs up to four extra memory accesses, which makes the hit ratio even more important (real CPUs also cache page-table entries in their data caches).

#### Code: simulating a small TLB

```python
from collections import OrderedDict


def tlb_hit_ratio(addresses, entries, page_size=4096):
    tlb = OrderedDict()                   # page -> frame, in LRU order
    hits = 0
    for a in addresses:
        page = a // page_size
        if page in tlb:
            hits += 1
            tlb.move_to_end(page)
        else:
            if len(tlb) == entries:
                tlb.popitem(last=False)   # evict the least recently used translation
            tlb[page] = page + 100        # pretend page-table walk
    return hits / len(addresses)


sequential = [4 * i for i in range(100_000)]                   # walking an int array
strided = [4096 * (i % 64) for i in range(100_000)]           # one access per page, 64 pages
print(round(tlb_hit_ratio(sequential, 16), 4))                 # 0.999: 1 miss per 1,024 ints
print(round(tlb_hit_ratio(strided, 16), 4))  # 0.0: 64 pages cycling through 16 entries
```

Sequential access misses once per page (1 in 1,024 `int`s). The strided pattern touches 64 pages in a cycle with only 16 entries, so LRU evicts each translation just before it is needed again: every access misses.

```cpp
// The same effect in C++: a column-wise walk of a row-major matrix jumps a whole row per step.
long long sumRows(const vector<int>& m, int n) {
    long long s = 0;
    for (int r = 0; r < n; ++r)
        // sequential: TLB and cache friendly
        for (int c = 0; c < n; ++c) s += m[size_t(r) * n + c];
    return s;
}
long long sumCols(const vector<int>& m, int n) {
    long long s = 0;
    for (int c = 0; c < n; ++c)
        // stride of n ints: many more misses
        for (int r = 0; r < n; ++r) s += m[size_t(r) * n + c];
    return s;
}
```

For a 4,096 × 4,096 matrix of `int`, each row is 16 KB (four pages), so the column walk touches a new page on every access and can be several times slower even though both loops do the same arithmetic.

#### Context switches and shootdowns

- Without tags, switching processes flushes the TLB, and the next process pays misses to warm it up.
- With ASIDs or PCIDs, entries from several processes coexist, and switches need no flush.
- When the kernel unmaps or changes a page used by threads on several cores, it sends inter-processor interrupts so each core invalidates its entry: a TLB shootdown, one reason `munmap` in multithreaded programs is costly.

#### TLB reach

With 1,536 entries and 4 KB pages, the TLB covers 6 MB. A database touching 64 GB will miss constantly; 2 MB huge pages raise reach to 3 GB with the same entries.

Connects to: paging, multi-level and inverted page tables, cache lines and locality, context switching.

### questions
Q: What is a TLB and why is it needed?
A: The translation lookaside buffer is a small, fast hardware cache of recent page-to-frame translations. Without it, every memory access under paging would need an extra memory access to read the page table; with a high TLB hit ratio, most accesses need only the data access.

Q: How do you compute the effective memory access time with a TLB?
A: For a single-level page table, EAT equals the hit ratio times (TLB time plus memory time) plus the miss ratio times (TLB time plus two memory times). For example, with 100 ns memory, a 20 ns TLB and an 80 percent hit ratio, EAT is 0.8 times 120 plus 0.2 times 220, which is 140 ns.

Q: What happens to the TLB on a context switch?
A: Its entries belong to the old process's address space, so they must be flushed, unless each entry is tagged with an address space identifier such as an ASID or PCID. Tagging lets entries from several processes coexist and avoids the refill cost after each switch.

Q: What is TLB reach and how can it be increased?
A: TLB reach is the amount of memory the TLB can map at once: the number of entries times the page size. It can be increased by adding entries or by using larger pages, such as 2 MB huge pages, which is why databases and virtual machines use them.

Q: Why do TLB hit ratios tend to be high?
A: Because of locality of reference. Programs execute instructions from the same pages repeatedly and access data sequentially or in small working sets, and one 4 KB page holds many consecutive items, so a few translations cover most accesses.

## os.memory.multi-level-and-inverted-page-tables
name: "Multi-level and inverted page tables"
importance: important
prereqs: [os.memory.paging]
scope: "reducing page table size"

### simple
A single flat page table for a big address space would be huge, mostly describing memory the program never uses. A multi-level page table is like a book index split into sections, where you only print the sections that have entries. An inverted page table flips the idea: it keeps one entry per physical frame, like a list of shelves saying which book is on each.

### interview
- Problem: a flat table needs one entry per possible page: 4 MB per process for 32-bit addresses and absurdly more for 64-bit ones, though most of the space is unused.
- **Multi-level (hierarchical) paging**: split the page number into several indices; the top-level table points to second-level tables, and so on. Tables for **unused regions are never allocated**.
- 32-bit x86: 10 + 10 + 12 bits (a page directory and page tables, each 1,024 × 4-byte entries = one 4 KB page). x86-64: **4 levels**, 9 + 9 + 9 + 9 + 12 = 48 bits, each table 512 × 8-byte entries = 4 KB (5 levels for 57-bit addresses).
- Cost: a TLB miss needs one memory access **per level**; the TLB and page-walk caches hide most of it.
- **Inverted page table**: one entry per **physical frame**, holding (process id, virtual page). Size scales with RAM, not with address spaces, and there is one table for the whole system. Lookup requires a **hash table** keyed by (pid, page). Sharing pages is awkward. Used by some PowerPC and IA-64 systems.
- **Hashed page tables** (hash the virtual page number to a chain of entries) are another option for sparse 64-bit spaces.

### deep
#### Worked example: splitting an x86-64 address

Address `0x00007f1234567abc`, 4-level paging with 4 KB pages:

| field | bits | value |
|---|---|---|
| level 4 index | 47 to 39 | 254 |
| level 3 index | 38 to 30 | 72 |
| level 2 index | 29 to 21 | 418 |
| level 1 index | 20 to 12 | 359 |
| offset | 11 to 0 | 0xabc |

The walk: CR3 → level-4 table entry 254 → level-3 table entry 72 → level-2 table entry 418 → level-1 table entry 359 → frame; add offset 0xabc.

```cpp
int main() {
    uint64_t va = 0x00007f1234567abcULL;
    for (int level = 4, shift = 39; level >= 1; --level, shift -= 9)
        // 9 bits each
        printf("level %d index %llu\n", level, (unsigned long long)((va >> shift) & 0x1ff));
    printf("offset 0x%llx\n", (unsigned long long)(va & 0xfff));
    // level 4 index 254, level 3 index 72, level 2 index 418, level 1 index 359, offset 0xabc
}
```

#### Why multi-level tables save space

A process using 8 MB of code and data near address 0 and a 1 MB stack near the top of its 48-bit space needs:

| table | how many |
|---|---|
| level 4 | 1 |
| level 3 | 2 (one for the low region, one for the high) |
| level 2 | 2 |
| level 1 | 4 for the 8 MB region (each covers 2 MB) + 1 for the stack |

That is 10 tables of 4 KB = 40 KB, instead of the $2^{36}$ entries a flat table would need (512 GB at 8 bytes each).

#### Inverted page table

| frame | pid | virtual page |
|---|---|---|
| 0 | 12 | 0x400 |
| 1 | 7 | 0x10 |
| 2 | 12 | 0x7ff |

To translate (pid 12, page 0x7ff), hash the pair to find the matching entry; its index (frame 2) is the frame number. The table's size is fixed by physical memory (for 16 GB of RAM with 4 KB frames, about 4 million entries), no matter how many processes run.

```python
def inverted_lookup(table, pid, page):
    index = {(p, v): frame for frame, (p, v) in enumerate(table)}   # the hash table
    return index.get((pid, page), "page fault")


table = [(12, 0x400), (7, 0x10), (12, 0x7FF)]
print(inverted_lookup(table, 12, 0x7FF), inverted_lookup(table, 7, 0x400))   # 2 page fault
```

#### Trade-offs

| | multi-level | inverted |
|---|---|---|
| size depends on | memory each process uses | physical RAM |
| lookup | one access per level (fast with TLB) | hash lookup, possible chains |
| sharing pages | easy (two tables point to one frame) | hard (one entry per frame) |
| common on | x86, ARM, RISC-V | some PowerPC, IA-64 |

Connects to: paging, TLB, virtual memory and demand paging, hash table internals.

### questions
Q: Why are multi-level page tables used?
A: A flat page table needs an entry for every possible page in the address space, which is millions of entries for 32-bit addresses and impossibly many for 64-bit ones, even though most pages are unused. A multi-level table only allocates lower-level tables for regions actually in use, saving a great deal of memory.

Q: How is a 48-bit virtual address translated on x86-64?
A: The address is split into four 9-bit indices and a 12-bit offset. Starting from the table pointed to by the CR3 register, each index selects an entry in the next level's table, and the last level gives the frame number, to which the offset is added.

Q: What is an inverted page table?
A: A single system-wide table with one entry per physical frame, recording which process and virtual page occupy that frame. Its size depends on physical memory rather than address spaces, but lookups need hashing, and sharing a frame between processes is awkward.

Q: What is the performance cost of multi-level page tables, and how is it hidden?
A: A TLB miss requires one memory access per level of the table, four on x86-64, before the data itself can be accessed. The TLB, which caches complete translations, and page-walk caches, which cache upper-level entries, make such full walks rare.

## os.memory.segmentation
name: "Segmentation"
importance: important
prereqs: [os.memory.paging]
scope: "segments vs pages, segmentation with paging"

### simple
Segmentation divides a program's memory into logical pieces of different sizes, such as code, data and stack, each with its own start and length. It is like a binder with labelled sections of whatever thickness each needs, rather than pages all cut to the same size. Each section can have its own rules, like "read only" for the code.

### interview
- A **segment** is a variable-size logical unit (code, globals, heap, stack, a library). A logical address is a pair **(segment number, offset)**.
- The **segment table** holds a **base** and a **limit** for each segment (plus protection bits). Translation: if offset ≥ limit, trap; otherwise physical = base + offset.
- Matches the programmer's view and gives per-segment protection and sharing (share a code segment read-only).
- Downside: **external fragmentation**, since segments are variable-size contiguous blocks.
- **Segmentation with paging**: each segment is itself paged (the classic Intel IA-32 design, and MULTICS), combining logical units with fragmentation-free placement.
- Modern x86-64 **flattens** segmentation (bases are zero for code and data), relies on paging, and keeps segment registers mostly for thread-local storage (FS, GS). "Segmentation fault" survives as the name for invalid memory access.

### deep
#### Segments vs pages

| | segmentation | paging |
|---|---|---|
| unit size | variable, fits the logical unit | fixed (4 KB) |
| visible to the programmer | yes: code, data, stack | no |
| fragmentation | external | internal |
| protection and sharing | natural, per logical unit | per page |
| address | (segment, offset) | a single number, split by bits |

#### Worked example

| segment | base | limit |
|---|---|---|
| 0 | 1400 | 1000 |
| 1 | 6300 | 400 |
| 2 | 4300 | 400 |
| 3 | 3200 | 1100 |
| 4 | 4700 | 1000 |

| logical address | check | physical |
|---|---|---|
| (2, 53) | 53 < 400 | 4300 + 53 = 4353 |
| (3, 852) | 852 < 1100 | 3200 + 852 = 4052 |
| (0, 1222) | 1222 ≥ 1000 | trap: addressing error |

```python
SEGMENTS = {0: (1400, 1000), 1: (6300, 400), 2: (4300, 400), 3: (3200, 1100), 4: (4700, 1000)}


def translate(segment, offset):
    base, limit = SEGMENTS[segment]
    if offset >= limit:
        raise MemoryError(f"offset {offset} beyond limit {limit} of segment {segment}")
    return base + offset


print(translate(2, 53), translate(3, 852))   # 4353 4052
try:
    translate(0, 1222)
except MemoryError as e:
    print(e)
```

#### Segmentation with paging

In IA-32, a logical address first goes through segmentation to a 32-bit linear address, then through two-level paging to a physical address:

```text
(selector, offset) --segment table--> linear address --page tables--> physical address
```

Each segment can grow in page-sized steps and needs no contiguous physical space. Operating systems like Linux set every segment's base to 0 and limit to the maximum, effectively turning segmentation off, and do everything with paging. In 64-bit mode the hardware ignores most segment bases, except FS and GS, which point at per-thread data.

Connects to: paging, logical vs physical addresses, fragmentation, process vs program.

### questions
Q: What is segmentation?
A: A memory management scheme that divides a process's address space into variable-sized logical segments, such as code, data and stack. An address is a segment number plus an offset, translated through a segment table holding each segment's base and limit.

Q: How does segmentation differ from paging?
A: Segments have variable sizes that match logical units and are visible to the programmer, which makes protection and sharing natural but causes external fragmentation. Pages are fixed-size and invisible to the programmer, which avoids external fragmentation but causes some internal fragmentation.

Q: How is a segmented address translated?
A: The segment number indexes the segment table to find the base and limit. If the offset is not less than the limit, the hardware traps to the operating system; otherwise the physical address is the base plus the offset.

Q: What is segmentation with paging?
A: A combined scheme where each segment is divided into pages: segmentation produces a linear address, which paging then maps to a physical frame. It keeps segments' logical structure and protection while avoiding external fragmentation, as in Intel IA-32 and MULTICS.

## os.memory.virtual-memory-and-demand-paging
name: "Virtual memory and demand paging"
importance: must
prereqs: [os.memory.tlb]
scope: "page faults and how they are handled"

### simple
Virtual memory lets a program use more memory than the computer physically has, by keeping only the parts in use in RAM and the rest on disk. Demand paging loads a page only when the program actually touches it, like a restaurant cooking a dish only when someone orders it rather than preparing the whole menu in advance. When a program touches a page that is not in RAM, the operating system quietly fetches it and the program continues.

### interview
- **Virtual memory** separates the logical address space from physical memory: a process can be larger than RAM, and only its **working set** needs to be resident.
- **Demand paging**: pages are loaded **only when first accessed**. The page table's **valid (present) bit** marks resident pages; touching a non-resident page raises a **page fault**.
- Handling a page fault: trap to the kernel → check the address is legal (else `SIGSEGV`) → find a free frame (or evict one with **page replacement**, writing it back if **dirty**) → read the page from disk or swap (or zero-fill a fresh one) → update the page table → **restart the faulting instruction**.
- **Minor** fault: the page is already in memory (page cache, a zero page, copy-on-write) and only needs mapping; microseconds. **Major** fault: disk I/O; milliseconds on disk, tens of microseconds on SSD.
- **EAT** $= (1 - p) \times m + p \times \text{fault time}$. With $m = 200$ ns and an 8 ms fault, $p = 1/1000$ gives about 8.2 µs, a **40×** slowdown; keeping the slowdown under 10% needs fewer than 1 fault in about 400,000 accesses.
- Benefits: faster startup, more processes in memory, lazy allocation, memory-mapped files, copy-on-write. Risk: **thrashing** when working sets do not fit.

### deep
#### Intuition

Programs rarely use all of their code and data at once: error handlers, rarely used features and huge arrays sit untouched. Loading everything up front wastes RAM and startup time. Demand paging loads nothing until it is needed, and page faults are the mechanism that makes "needed" visible to the OS.

#### Worked example: a page fault, step by step

| step | who | action |
|---|---|---|
| 1 | CPU | `mov eax, [0x5000]`; the MMU finds page 5's entry with valid bit 0 |
| 2 | CPU | raises a page fault and saves the faulting instruction's address |
| 3 | kernel | looks up page 5 in the process's memory map: it belongs to a mapped file, so the access is legal |
| 4 | kernel | finds a free frame (or evicts a victim, writing it to disk first if dirty) |
| 5 | kernel | starts a disk read into the frame and puts the process to sleep; other processes run |
| 6 | disk | interrupts when the read completes |
| 7 | kernel | sets page 5 → frame, valid = 1; marks the process ready |
| 8 | CPU | re-executes `mov eax, [0x5000]`, which now succeeds |

#### The cost

$$EAT = (1 - p)\,m + p\,f$$

With $m = 200$ ns and fault service $f = 8$ ms:

| fault rate $p$ | EAT | slowdown |
|---|---|---|
| 0 | 200 ns | none |
| 1 in 400,000 | ≈ 220 ns | 10% |
| 1 in 1,000 | ≈ 8,200 ns | 41× |

The fault rate must be tiny, which is why locality and good replacement policies matter so much.

#### Code: watching demand paging happen

```cpp
#include <sys/mman.h>
#include <sys/resource.h>

long minorFaults() {
    rusage u;
    getrusage(RUSAGE_SELF, &u);
    return u.ru_minflt;
}

int main() {
    const size_t size = 64 << 20;                                        // reserve 64 MB
    char* p = static_cast<char*>(mmap(nullptr, size, PROT_READ | PROT_WRITE,
                                      MAP_PRIVATE | MAP_ANONYMOUS, -1, 0));
    long before = minorFaults();
    for (size_t i = 0; i < size / 2; i += 4096) p[i] = 1;                 // touch half the pages
    long after = minorFaults();
    printf("touched %zu pages, minor faults %ld\n", size / 2 / 4096, after - before);
    munmap(p, size);
}
```

A test run printed "touched 8192 pages, minor faults 8192": `mmap` only reserved address space, and each first touch faulted in one zero-filled page. The untouched half never used any RAM.

```python
def demand_paging(refs, frames):
    resident, faults = [], 0
    for page in refs:
        if page not in resident:
            faults += 1                      # page fault: bring the page in
            if len(resident) == frames:
                resident.pop(0)              # evict the oldest (FIFO, for simplicity)
            resident.append(page)
    return faults


print(demand_paging([0, 1, 0, 2, 0, 1, 3, 0], frames=3))   # 5
```

#### What makes it work

- **Locality of reference**: programs use a small set of pages at a time (loops, stack frames, sequential data).
- **Restartable instructions**: the hardware must be able to re-run the faulting instruction as if nothing happened.
- **Backing store**: executables and mapped files are paged in from their files; anonymous memory goes to swap when evicted.

#### Pitfalls

- Believing `malloc` of 1 GB uses 1 GB of RAM immediately: pages are allocated on first touch (overcommit).
- Ignoring major faults in latency-sensitive code: preload with `mlock` or `MAP_POPULATE`, or touch memory at startup.

Connects to: page replacement, thrashing and working sets, paging, TLB, copy-on-write and memory-mapped files, interrupts, traps and exceptions.

### questions
Q: What is demand paging?
A: A virtual memory technique where a page is loaded into memory only when the program first accesses it, instead of loading the whole program at start. Pages not in memory are marked invalid, and touching one triggers a page fault that brings it in.

Q: What steps does the OS take to handle a page fault?
A: It traps into the kernel, checks the faulting address is valid for the process, finds a free frame or evicts a victim page (writing it out if dirty), reads the needed page from disk or zero-fills it, updates the page table entry to valid, and restarts the instruction that faulted.

Q: What is the difference between a minor and a major page fault?
A: A minor fault is resolved without disk I/O, for example when the page is already in the page cache, is a fresh zero page or needs a copy-on-write copy; it costs microseconds. A major fault requires reading the page from disk or swap and costs far more, milliseconds on a hard disk.

Q: How do you calculate effective access time with page faults?
A: EAT equals (1 minus p) times the memory access time plus p times the page fault service time, where p is the fault rate. With 200 ns memory and an 8 ms fault time, a fault rate of 1 in 1,000 gives about 8.2 microseconds, around 40 times slower than no faults.

Q: Why can a process's virtual memory be larger than physical memory?
A: Only the pages a process is actively using must be in RAM. The rest live on disk, in the executable or in swap, and are brought in on demand while less-used pages are evicted, so the logical address space is not limited by physical memory.

## os.memory.page-replacement
name: "Page replacement"
importance: must
prereqs: [os.memory.virtual-memory-and-demand-paging]
scope: "FIFO, LRU, Optimal, Clock; Belady's anomaly"

### simple
When memory is full and a new page is needed, the operating system must choose an old page to throw out. It is like a small desk that holds only three books: when you need a fourth, you decide which one goes back on the shelf. A good rule removes the book you won't need for the longest time, so you rarely have to fetch it again.

### interview
- On a page fault with no free frame, pick a **victim**; if it is **dirty** it must be written back first, so clean victims are cheaper.
- **FIFO**: evict the page loaded earliest. Simple, but it can evict heavily used pages and suffers **Belady's anomaly**: more frames can cause **more** faults.
- **Optimal (OPT, MIN)**: evict the page whose next use is **farthest in the future**. Fewest faults possible, but needs the future, so it is only a benchmark.
- **LRU**: evict the page **least recently used**; a good approximation of OPT thanks to locality. A **stack algorithm**, so no Belady's anomaly. Exact LRU is too costly in hardware (a timestamp or list update on every access).
- **Clock (second chance)**: frames in a circle with a **reference bit**; the hand clears 1s and evicts the first 0. A cheap LRU approximation used by real kernels (with variants using the dirty bit too).
- Classic numbers, reference string 7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1 with 3 frames: **FIFO 15, LRU 12, OPT 9** faults (Clock 14). Belady: 1 2 3 4 1 2 5 1 2 3 4 5 with FIFO gives **9 faults with 3 frames and 10 with 4**.

### deep
#### Worked example: LRU with 3 frames

Reference string: 7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1

| ref | frames after | fault? | evicted (least recently used) |
|---|---|---|---|
| 7 | 7 | F | |
| 0 | 7 0 | F | |
| 1 | 7 0 1 | F | |
| 2 | 2 0 1 | F | 7 |
| 0 | 2 0 1 | | |
| 3 | 2 0 3 | F | 1 |
| 0 | 2 0 3 | | |
| 4 | 4 0 3 | F | 2 |
| 2 | 4 0 2 | F | 3 |
| 3 | 4 3 2 | F | 0 |
| 0 | 0 3 2 | F | 4 |
| 3 | 0 3 2 | | |
| 2 | 0 3 2 | | |
| 1 | 1 3 2 | F | 0 |
| 2 | 1 3 2 | | |
| 0 | 1 0 2 | F | 3 |
| 1 | 1 0 2 | | |
| 7 | 1 0 7 | F | 2 |
| 0 | 1 0 7 | | |
| 1 | 1 0 7 | | |

12 faults. On the same string FIFO gives 15, Clock 14 and OPT 9.

#### Belady's anomaly with FIFO

String 1 2 3 4 1 2 5 1 2 3 4 5:

| frames | FIFO faults |
|---|---|
| 3 | 9 |
| 4 | 10 |

With 4 frames, FIFO keeps 1 and 2 resident through the second "1 2" (hits), but then 5 evicts 1, and every later reference misses. LRU and OPT are **stack algorithms** (the pages held with n frames are always a subset of those held with n + 1), so they never show the anomaly: LRU gives 10 and 8 faults on this string.

#### Code: FIFO, LRU and OPT

```cpp
int faults(const vector<int>& refs, int frames, const string& policy) {
    vector<int> mem;                                   // resident pages
    vector<int> lastUse(1000, -1);                     // for LRU (page ids < 1000 here)
    int count = 0;
    for (int t = 0; t < (int)refs.size(); ++t) {
        int p = refs[t];
        auto it = find(mem.begin(), mem.end(), p);
        if (it == mem.end()) {
            ++count;
            if ((int)mem.size() == frames) {
                int victim = 0;
                if (policy == "LRU") {
                    for (int i = 1; i < frames; ++i)
                        if (lastUse[mem[i]] < lastUse[mem[victim]]) victim = i;
                } else if (policy == "OPT") {
                    int farthest = -1;
                    for (int i = 0; i < frames; ++i) {
                        int next = find(refs.begin() + t + 1, refs.end(), mem[i]) - refs.begin();
                        if (next > farthest) { farthest = next; victim = i; }
                    }
                }                                      // FIFO: victim 0 is the oldest
                mem.erase(mem.begin() + victim);
            }
            mem.push_back(p);
        }
        lastUse[p] = t;
    }
    return count;
}

int main() {
    vector<int> refs = {7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2, 1, 2, 0, 1, 7, 0, 1};
    for (string p : {"FIFO", "LRU", "OPT"}) cout << p << " " << faults(refs, 3, p) << "\n";
    // FIFO 15, LRU 12, OPT 9
    vector<int> belady = {1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5};
    cout << faults(belady, 3, "FIFO") << " " << faults(belady, 4, "FIFO") << "\n";   // 9 10
}
```

#### In real kernels

Linux keeps active and inactive lists (a two-list LRU approximation, with a newer multi-generational LRU), prefers evicting clean page-cache pages over dirty or anonymous ones, and writes dirty pages back in the background so eviction rarely waits on I/O.

Connects to: virtual memory and demand paging, thrashing and working sets, LRU cache, caching.

### questions
Q: What is the optimal page replacement algorithm, and why is it not used in practice?
A: It evicts the page that will not be used for the longest time in the future, which gives the fewest possible page faults. It needs knowledge of future references, which the OS does not have, so it serves only as a benchmark for comparing other algorithms.

Q: What is Belady's anomaly?
A: The counterintuitive situation where giving a process more page frames increases its number of page faults. It happens with FIFO: the reference string 1 2 3 4 1 2 5 1 2 3 4 5 causes 9 faults with 3 frames but 10 with 4. Stack algorithms like LRU and OPT never show it.

Q: Why is exact LRU rarely implemented, and what approximates it?
A: Exact LRU would require updating a timestamp or reordering a list on every memory access, which is far too expensive in hardware. The clock or second-chance algorithm approximates it using a reference bit per page that the hardware sets on access and the OS clears as its hand sweeps.

Q: How does the clock algorithm work?
A: Frames are arranged in a circle with a hand pointing at one. On a fault, if the page under the hand has its reference bit set, the bit is cleared and the hand moves on, giving it a second chance; the first page found with the bit clear is evicted and replaced.

Q: With the reference string 7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1 and 3 frames, how many faults do FIFO, LRU and OPT give?
A: FIFO causes 15 page faults, LRU causes 12 and the optimal algorithm causes 9. LRU comes much closer to optimal than FIFO because it keeps recently used pages that are likely to be used again.

## os.memory.thrashing-and-working-sets
name: "Thrashing and working sets"
importance: must
prereqs: [os.memory.page-replacement]
scope: "causes and cures"

### simple
Thrashing is when a computer spends almost all its time swapping pages between memory and disk and almost no time doing real work. It is like trying to cook in a kitchen so small that you must put away one ingredient every time you take out another. The fix is to give each program room for the set of pages it is actively using, or run fewer programs at once.

### interview
- **Thrashing**: processes don't have enough frames for the pages they are actively using, so they fault constantly, each fault evicting a page that is needed again soon. The CPU waits on disk and utilization collapses.
- The classic trap: low CPU utilization makes a naive scheduler **admit more processes**, which takes frames from everyone and makes thrashing worse.
- **Locality model**: a process moves between localities (sets of pages used together). If its frames can hold its current locality, faults stay rare.
- **Working set** $W(t, \Delta)$: the pages referenced in the last $\Delta$ references. If the sum of working-set sizes exceeds available frames, **suspend (swap out)** a process; otherwise, there is room to admit another.
- **Page-fault frequency (PFF)**: set upper and lower bounds on each process's fault rate; above the upper bound give it more frames, below the lower bound take frames away; if no frames are free, suspend a process.
- Other cures: add RAM, reduce the degree of multiprogramming, use **local** replacement (a process evicts only its own pages), improve program locality. On Linux, heavy swapping plus high I/O wait and low useful CPU are the symptoms, and the OOM killer is the last resort.

### deep
#### Intuition

A process needs a certain set of pages to run a phase of its work. Give it fewer frames than that and every fault throws out something it will need moments later, so it faults again, and again. Beyond a certain degree of multiprogramming, adding processes makes the whole system slower, not faster.

#### The thrashing curve

```text
CPU utilization
 ^
 |          ______
 |       __/      \
 |     _/          \
 |   _/             \___
 |  /                    \____ thrashing
 +------------------------------> number of processes (degree of multiprogramming)
```

Utilization rises as more processes keep the CPU busy, peaks, and then collapses once their combined working sets exceed memory.

#### Worked example: the working set

Reference string (time 0 to 15): 1 2 3 3 2 1 4 4 4 5 5 6 5 6 6 5, window $\Delta = 5$.

| time t | last 5 references | working set | size |
|---|---|---|---|
| 5 | 2 3 3 2 1 | {1, 2, 3} | 3 |
| 15 | 6 5 6 6 5 | {5, 6} | 2 |

At time 5 the process needs 3 frames; by time 15 it has moved to a new locality needing only 2. If three such processes each need 3 frames and only 8 are available, the OS should suspend one rather than let all three thrash.

```python
def working_set(refs, t, delta):
    return set(refs[max(0, t - delta + 1): t + 1])


refs = [1, 2, 3, 3, 2, 1, 4, 4, 4, 5, 5, 6, 5, 6, 6, 5]
print(sorted(working_set(refs, 5, 5)), sorted(working_set(refs, 15, 5)))   # [1, 2, 3] [5, 6]


def admit(working_set_sizes, frames):
    """Admission control: run processes while their working sets fit."""
    running, used = [], 0
    for pid, size in working_set_sizes.items():
        if used + size <= frames:
            running.append(pid)
            used += size
    return running


print(admit({"A": 3, "B": 3, "C": 3}, frames=8))   # ['A', 'B']: C waits instead of thrashing
```

#### Choosing $\Delta$

| $\Delta$ | effect |
|---|---|
| too small | misses part of the locality; still faults |
| too large | spans several localities; overestimates and wastes frames |
| infinite | the whole program: no point in paging |

Tracking exact working sets is expensive, so kernels approximate with reference bits sampled on timer interrupts, or use PFF, which only needs fault counts.

#### Page-fault frequency

| a process's fault rate | action |
|---|---|
| above the upper bound | give it more frames |
| between the bounds | leave it |
| below the lower bound | take frames away |
| above the bound and no free frames | suspend some process |

#### Recognizing thrashing

- Disk (swap) I/O pegged, CPU mostly in I/O wait, `vmstat` showing high `si`/`so` (swap in and out).
- Throughput collapses as load increases.
- The fix in production is usually more memory, fewer concurrent workers, or smaller per-worker memory, not a smarter algorithm.

Connects to: page replacement, virtual memory and demand paging, scheduling criteria, locality of reference.

### questions
Q: What is thrashing?
A: A state in which processes do not have enough frames for the pages they are actively using, so they page fault continuously and spend most of their time waiting for pages to be swapped in and out. CPU utilization drops sharply while disk activity is very high.

Q: Why can increasing the number of processes cause thrashing?
A: More processes means fewer frames per process. Once the frames can no longer hold each process's working set, fault rates rise, CPU utilization falls, and a naive scheduler that responds to low utilization by admitting more processes makes the problem worse.

Q: What is the working set model?
A: The working set of a process at time t is the set of pages it referenced in the last delta references, approximating its current locality. The OS tries to keep each running process's working set in memory and suspends processes when the total working-set size exceeds available frames.

Q: How does the page-fault frequency approach control thrashing?
A: The OS measures each process's page fault rate against upper and lower bounds. If the rate is too high, the process gets more frames; if too low, frames are taken away. If a process needs more frames and none are free, a process is suspended.

Q: How would you fix thrashing on a production server?
A: Reduce memory demand: run fewer concurrent processes or worker threads, lower per-process memory use such as cache sizes, or add RAM. Local replacement policies and admission control based on working sets prevent one process from causing the others to thrash.

## os.memory.copy-on-write-and-memory-mapped-files
name: "Copy-on-write and memory-mapped files"
importance: important
prereqs: [os.memory.virtual-memory-and-demand-paging]
scope: "Copy-on-write and memory-mapped files"

### simple
Copy-on-write lets two processes share the same memory until one of them changes it, and only then makes a private copy. It is like two students sharing one textbook until one wants to write notes in it, at which point that student gets their own photocopy of the page. Memory-mapped files use the same page tricks to make a file on disk look like ordinary memory you can read and write.

### interview
- **Copy-on-write (COW)**: pages are shared **read-only** between processes (after `fork`, or between a mapping and its file); the first **write** triggers a page fault, and the kernel copies just that page and makes it writable for the writer.
- COW makes `fork` fast and lets unchanged pages stay shared forever (for example Redis forks to write snapshots while the parent keeps serving).
- **Memory-mapped files** (`mmap`): map a file into the address space; reads and writes become memory accesses; pages are loaded on demand through page faults and cached in the **page cache**.
- `MAP_SHARED`: writes go to the file and are visible to other processes mapping it (written back lazily or with `msync`). `MAP_PRIVATE`: writes are copy-on-write and never reach the file.
- Benefits: no `read`/`write` system call per access, no extra copy between kernel and user buffers, easy random access, shared libraries loaded once for all processes. Costs: page-fault overhead for scattered access, awkward error handling (I/O errors become signals like `SIGBUS`), and resizing files is clumsy.
- Anonymous `mmap` (not backed by a file) is how large `malloc` blocks and shared memory between related processes are created.

### deep
#### Copy-on-write, step by step

| step | parent's page X | child's page X | physical frames used |
|---|---|---|---|
| after `fork` | frame 12, read-only | frame 12, read-only | 1 |
| parent reads X | frame 12 | frame 12 | 1 |
| child writes X | frame 12 | fault, kernel copies to frame 40, writable | 2 |
| parent writes X | frame 12, writable again (last sharer) | frame 40 | 2 |

#### Code: a file edited through memory

```cpp
#include <fcntl.h>
#include <sys/mman.h>
#include <unistd.h>

int main() {
    int fd = open("greeting.txt", O_RDWR | O_CREAT | O_TRUNC, 0644);
    const char text[] = "hello mmap\n";
    if (fd < 0 || write(fd, text, sizeof text - 1) < 0) return 1;
    size_t len = sizeof text - 1;
    char* p = static_cast<char*>(mmap(nullptr, len, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0));
    for (size_t i = 0; i < 5; ++i) p[i] = toupper(p[i]);     // plain memory writes change the file
    msync(p, len, MS_SYNC);                                  // flush to the file now
    munmap(p, len);
    close(fd);
    ifstream in("greeting.txt");
    string line;
    getline(in, line);
    cout << line << "\n";                                    // HELLO mmap
}
```

#### read versus mmap

| | `read` into a buffer | `mmap` |
|---|---|---|
| copies | disk → page cache → your buffer | disk → page cache, mapped directly |
| per access | a system call per chunk | none after the page is mapped |
| random access | `lseek` + `read` each time | pointer arithmetic |
| errors | return codes | signals (`SIGBUS`) |
| best for | streaming, small or unknown sizes | large files with random access, sharing |

#### Where you meet these every day

- Every executable and shared library is `mmap`ed: code pages are loaded on demand and shared across processes.
- Databases (LMDB, older MongoDB engines) and search engines (Lucene) map their files.
- `fork` in shells and servers relies on COW; Python's multiprocessing on Linux does too, although reference-count updates can trigger copies of pages holding objects.

Connects to: fork, exec and wait, virtual memory and demand paging, inter-process communication, buffering, caching and spooling.

### questions
Q: How does copy-on-write make fork efficient?
A: Instead of copying the parent's memory, fork makes both processes share the same physical pages marked read-only. Only when one of them writes to a page does a fault occur, and the kernel copies that single page. Pages that are never written, and everything discarded by an immediate exec, are never copied.

Q: What is a memory-mapped file?
A: A file mapped into a process's virtual address space with mmap, so that reading and writing memory in that range reads and writes the file. Pages are loaded on demand through page faults and cached in the kernel's page cache.

Q: What is the difference between MAP_SHARED and MAP_PRIVATE?
A: With MAP_SHARED, writes to the mapping are carried through to the underlying file and seen by other processes that map it. With MAP_PRIVATE, writes trigger copy-on-write, so the process gets its own modified copy of the page and the file is not changed.

Q: When is mmap faster than read, and when is it not?
A: mmap avoids a system call per access and the copy from the kernel buffer into a user buffer, which helps large files with random or repeated access. For simple sequential streaming, read with a large buffer is often as fast or faster, since mmap pays page-fault and mapping overhead.

## os.memory.stack-vs-heap-memory
name: "Stack vs heap memory"
importance: important
scope: "allocation, lifetime, fragmentation"

### simple
The stack is memory for short-lived local variables that are created and destroyed automatically as functions start and finish. The heap is a larger pool where you request memory explicitly and it lasts until you free it. The stack is like a stack of plates at a buffet, always taken from and returned to the top, while the heap is like a storage unit you rent and must remember to give back.

### interview
- **Stack**: one per thread; holds function **frames** (locals, arguments, return addresses, saved registers). Allocation is just moving the **stack pointer**, so it is extremely fast, and memory is freed automatically when the function returns (**LIFO lifetime**).
- **Heap**: shared by all threads of a process; memory from `malloc`/`new` (or the runtime, in Java and Python) with **arbitrary lifetime**, freed by `free`/`delete`, destructors, or a garbage collector.
- Stack size is **limited** (commonly 8 MB for the main thread on Linux, `ulimit -s`; less for other threads, 1 MB by default on Windows), so deep recursion or huge local arrays cause a **stack overflow**. The heap can grow to the size of available virtual memory.
- Heap allocation is slower (allocator bookkeeping, possible locks, possible system calls) and suffers **fragmentation**; the stack never fragments.
- Bugs: stack: returning a pointer to a local, overflow; heap: **leaks**, double free, use-after-free, dangling pointers.
- Java and Python keep objects on the heap and only references and primitive locals on the stack (the JIT may still allocate non-escaping objects on the stack).

### deep
#### Side by side

| | stack | heap |
|---|---|---|
| allocation | move the stack pointer (one instruction) | allocator searches free lists |
| freeing | automatic on return | explicit, RAII, or garbage collection |
| lifetime | the function call | until freed |
| size | small, fixed per thread | large, grows on demand |
| sharing | private to the thread | visible to all threads |
| fragmentation | none | yes |
| typical bugs | overflow, dangling pointer to a dead frame | leak, double free, use-after-free |

#### Code

```cpp
// sketch: a classic bug
int* broken() {
    int local = 42;
    return &local;                           // the frame is gone after return (compilers warn)
}
```

```cpp
unique_ptr<int> fine() {
    return make_unique<int>(42);             // heap: lives until the unique_ptr is destroyed
}

int depth = 0;
void recurse(int n) {
    char buffer[1024];                       // 1 KB per frame
    buffer[0] = static_cast<char>(n);
    depth = max(depth, n);
    if (n < 1000) recurse(n + 1);  // about 1 MB in total: fine; a million levels would overflow
}

int main() {
    auto p = fine();
    recurse(1);
    cout << *p << " " << depth << "\n";      // 42 1000
    vector<int> big(10'000'000);  // 40 MB: the vector object is on the stack, its data on the heap
    cout << big.size() << "\n";
}
```

The `broken` function compiles (with a warning) but using its result is undefined behavior: the next call reuses that stack memory.

#### Worked example: a call's stack frames

```text
main():      [ return address | p | big ]
  recurse(1):   [ return address | n=1 | buffer[1024] ]
    recurse(2):    [ return address | n=2 | buffer[1024] ]
      ...
```

Each call pushes a frame; each return pops it by moving the stack pointer back. Nothing is "freed" item by item, which is why the stack is so fast.

#### Python's view

```python
import sys

print(sys.getrecursionlimit())     # 1000 by default: Python guards its own stack


def depth(n):
    return n if n == 0 else depth(n - 1)


try:
    depth(10_000)
except RecursionError as e:
    print("RecursionError:", e)
```

Python objects always live on the heap; the interpreter's frames hold references to them.

#### Choosing

- Use the stack for small, short-lived values with sizes known at compile time.
- Use the heap for large data, data whose size is known only at runtime, and data that must outlive the function or be shared between threads.
- In C++, prefer containers and smart pointers so heap memory is released automatically.

Connects to: process vs program, how malloc works, object lifecycle, recursion, fragmentation.

### questions
Q: What are the main differences between stack and heap memory?
A: The stack holds function call frames and local variables, is allocated and freed automatically in last-in, first-out order by moving the stack pointer, is small and private to each thread. The heap holds dynamically allocated memory with lifetimes chosen by the program, is larger and shared among threads, is slower to allocate and can fragment.

Q: Why is stack allocation faster than heap allocation?
A: Allocating on the stack only moves the stack pointer by the size of the frame, and freeing moves it back when the function returns. Heap allocation requires the allocator to search for a suitable free block, maintain metadata and possibly take a lock or ask the kernel for more memory.

Q: What causes a stack overflow?
A: Using more stack than its fixed size allows, typically through very deep or infinite recursion or very large local arrays. When the stack pointer runs past the end of the stack into a guard page, the process receives a fault and usually crashes.

Q: Why is returning a pointer to a local variable a bug?
A: The local variable lives in the function's stack frame, which is released when the function returns and reused by later calls. The returned pointer then points to memory that may be overwritten at any time, so using it is undefined behavior.

## os.memory.how-malloc-works
name: "How malloc works"
importance: advanced
prereqs: [os.memory.stack-vs-heap-memory]
scope: "free lists, bins, brk and mmap"

### simple
malloc is the library function that hands out pieces of the heap and takes them back when you call free. It works like a warehouse manager who keeps lists of empty shelf spaces sorted by size and only asks the landlord for more space when the lists run dry. Asking the operating system for memory is slow, so malloc reuses freed space whenever it can.

### interview
- `malloc` manages memory in **user space**; it asks the kernel for memory only in bulk: **`brk`/`sbrk`** grows the classic heap segment, and **`mmap`** creates separate mappings (glibc uses `mmap` for large requests, 128 KB by default, adjusted dynamically).
- Each block (**chunk**) has a small **header** (size and flags) before the returned pointer; `free` reads it to know the size.
- Freed chunks go on **free lists**, organized into **bins** by size: in glibc, per-thread **tcache** bins, fast bins, small bins, large bins and an unsorted bin. Allocation looks for a fitting free chunk before growing the heap.
- Freed neighbors are **coalesced** into larger chunks to limit fragmentation; big chunks are **split** to satisfy smaller requests.
- Multiple **arenas** reduce lock contention between threads. Alternatives such as **jemalloc** and **tcmalloc** use size classes and per-thread caches for speed and lower fragmentation.
- Bugs such as double free, use-after-free and heap overflows corrupt these internal lists, which is why they crash later in unrelated places (and why they are exploitable).

### deep
#### A tiny first-fit allocator

```cpp
// A toy allocator over a fixed arena: first fit, splitting and coalescing.
class Arena {
    struct alignas(16) Block { size_t size; bool free; Block* next; };   // header before each block
    alignas(16) unsigned char mem[4096];
    Block* head;
public:
    Arena() : head(reinterpret_cast<Block*>(mem)) {
        *head = {sizeof mem - sizeof(Block), true, nullptr};     // one big free block
    }

    void* alloc(size_t n) {
        n = (n + 15) & ~size_t(15);                              // keep 16-byte alignment
        for (Block* b = head; b; b = b->next) {
            if (!b->free || b->size < n) continue;               // first fit
            if (b->size >= n + sizeof(Block) + 16) {             // split off the remainder
                auto* rest = reinterpret_cast<Block*>(reinterpret_cast<unsigned char*>(b + 1) + n);
                *rest = {b->size - n - sizeof(Block), true, b->next};
                b->size = n;
                b->next = rest;
            }
            b->free = false;
            return b + 1;                                        // memory right after the header
        }
        return nullptr;  // real malloc would call brk or mmap
    }

    void release(void* p) {
        Block* b = static_cast<Block*>(p) - 1;                   // step back to the header
        b->free = true;
        for (Block* c = head; c; c = c->next)                    // coalesce free neighbors
            while (c->free && c->next && c->next->free) {
                c->size += sizeof(Block) + c->next->size;
                c->next = c->next->next;
            }
    }

    size_t largestFree() const {
        size_t best = 0;
        for (Block* b = head; b; b = b->next) if (b->free) best = max(best, b->size);
        return best;
    }
};

int main() {
    Arena a;
    void* x = a.alloc(1000);
    void* y = a.alloc(1000);
    void* z = a.alloc(1000);
    cout << a.largestFree() << "\n";   // what is left after three blocks and their headers
    a.release(x);
    a.release(y);                      // x and y merge into one free block
    void* big = a.alloc(2000);         // fits in the merged space: coalescing at work
    cout << (big == x) << "\n";        // 1
    a.release(z);
    a.release(big);
    cout << a.largestFree() << "\n";   // the whole arena is one free block again
}
```

#### What real allocators add

| feature | why |
|---|---|
| size-class bins | find a fitting chunk in O(1) instead of scanning |
| per-thread caches (tcache) | most allocations need no lock |
| `mmap` for large blocks | returned to the OS immediately on `free` |
| `brk` for the main heap | cheap growth of one contiguous region |
| arenas | threads allocate from different pools in parallel |

Connects to: stack vs heap memory, fragmentation, contiguous allocation, copy-on-write and memory-mapped files.

### questions
Q: How does malloc get memory from the operating system?
A: It requests memory in large chunks rather than per call: by moving the program break with brk or sbrk to grow the heap for small allocations, and by creating separate anonymous mappings with mmap for large allocations, which can be returned to the kernel directly when freed.

Q: How does free know how much memory to release?
A: malloc stores a small header just before the pointer it returns, holding the block's size and status flags. free steps back from the pointer to read that header and puts the block on the appropriate free list.

Q: Why does malloc coalesce free blocks?
A: Adjacent small free blocks cannot satisfy a larger request on their own. Merging neighbors into one bigger block when memory is freed reduces external fragmentation and lets future large requests be served without growing the heap.
